# Безопасность и контроль доступа (Security & Access Control)

Данный документ описывает текущую модель безопасности IIoT-системы мониторинга и супервизорного управления, документирует известные архитектурные ограничения и формулирует обязательные требования к периметру при развертывании в производственной среде.

---

## 1. Архитектурная модель доверия (Current Trust Model)

Система изначально спроектирована для работы в изолированном сегменте промышленной сети (OT / Industrial Automation VLAN) с **моделью доверенного окружения**:

- Компоненты (`IIoT.Collector`, `IIoT.WebApi`, `iiot_admin`, `TimescaleDB`) функционируют во внутренней Docker-сети или локальном контуре.
- Взаимодействие между компонентами оптимизировано под минимальную задержку передачи телеметрии (Sub-second latency) и надёжность опроса Modbus TCP.

---

## 2. Задокументированные ограничения безопасности

### 2.1. Отсутствие встроенной аутентификации и RBAC
- В `IIoT.WebApi` **не реализованы** механизмы аутентификации (JWT, OAuth2/OIDC, mTLS, сессионные cookies, API-ключи).
- В системе **отсутствует ролевая модель (RBAC)**: любой сетевой субъект, имеющий доступ к порту WebApi (`8080`) или веб-интерфейсу (`3000`), обладает равными правами на чтение телеметрии, изменение конфигурации и подачу команд.
- Идентификатор оператора (`OperatorId`), передаваемый при отправке команд управления, является информационным строковым полем клиентского запроса (по умолчанию `"admin"` или значение из локальных настроек клиента). Сервер фиксирует это значение в журнале `device_commands` для аудита, но **не проверяет подлинность** оператора криптографически.

### 2.2. Риски эндпоинтов супервизорного управления (Write-Command Endpoints)
- **Эндпоинты:**
  - REST API: `POST /api/control/write`
  - SignalR Hub: `/hubs/control` (`SendCommand`)
- **Угроза:** Несанкционированный доступ к указанным эндпоинтам позволяет злоумышленнику осуществлять запись в физические регистры оборудования (Modbus Coils и Holding Registers). В условиях реального технологического объекта это может привести к сбою технологического процесса, аварийному останову или повреждению оборудования.
- **Текущие встроенные проверки бэкенда:**
  - Валидация типа регистра: запись разрешена строго для регистров типа `COIL` (Coil 0x) и `HOLDING_REGISTER` (Holding Register 4x). Попытки записи в `INPUT_STATUS` (1x) и `INPUT_REGISTER` (3x) отклоняются на уровне валидации с кодом HTTP 400.
  - Проверка доступности коллектора: команда отклоняется (`503 Service Unavailable`), если сборщик данных не находится в статусе `Online` или не подтверждал heartbeat более 15 секунд.
  - Персистентный аудит: каждая принятая команда регистрируется в таблице `device_commands` с уникальным `command_id` (UUID), временной меткой создания, временем обработки и статусом исполнения (`PENDING` -> `PROCESSING` -> `SUCCESS` / `FAILED`).

## 3. Требования к периметру и защите в Production

Поскольку система не реализует аутентификацию на прикладном уровне, **безопасность целиком возлагается на сетевой периметр и внешние шлюзы безопасности (Defense-in-Depth)**.

### 3.1. Сетевая изоляция
1. **Порты СУБД и Modbus:**
   - Порт PostgreSQL (`5432`) и порт Modbus-устройств/симулятора (`502` / `5020`) **категорически запрещено** публиковать в глобальную сеть (WAN). В `docker-compose.yml` доступ к ним должен быть ограничен локальным хостом (`127.0.0.1:5432`) либо внутренней сетью Docker.
2. **Сегментация сети:**
   - Сервер сбора (`Collector`) должен размещаться в промышленном сегменте сети с доступом к ПЛК/контроллерам через межсетевой экран (L3/L4 Firewall) с белым списком IP-адресов.

### 3.2. Аутентификация на периметре (Reverse Proxy / Cloudflare Access)
При необходимости удаленного доступа к системе мониторинга и админ-панели доступ должен быть организован исключительно через внешний шлюз с аутентификацией:

1. **Cloudflare Zero Trust / Cloudflare Access (рекомендуется при использовании Cloudflare Tunnel):**
   - Настроить Access Application для публичного домена админки и API.
   - Включить двухфакторную аутентификацию (2FA/MFA) через корпоративный IdP (Google Workspace, GitHub, SAML/OIDC).
   - Ограничить доступ политиками allowlist по корпоративным email-адресам.
2. **Reverse Proxy (Nginx / Traefik / Caddy / Envoy):**
   - Настроить терминацию TLS/HTTPS.
   - Включить HTTP Basic Auth, forward-auth (Authelia, Keycloak) или взаимную аутентификацию по сертификатам (mTLS).
   - Настроить ограничение частоты запросов (Rate Limiting) для пути `/api/control/*` для защиты от переполнения очереди команд.

### 3.3. Рекомендации по развитию системы (Roadmap)
При переводе системы в класс критически важных промышленных систем рекомендуется следующий план доработки:
1. **Аутентификация WebApi:** Интеграция ASP.NET Core Authentication (`Microsoft.AspNetCore.Authentication.JwtBearer`).
2. **Привязка OperatorId:** Извлечение идентификатора оператора непосредственно из claims валидированного JWT (`User.FindFirst(ClaimTypes.NameIdentifier)`), исключая ручной ввод на клиенте.
3. **RBAC:** Разделение ролей `Viewer` (только чтение телеметрии и дашбордов), `Engineer` (настройка тегов и опросников) и `Operator` (право супервизорного управления с подтверждением действия).
