
Система построена на трех уровнях: Конфигурация оборудования, Поток метрик и Системные настройки. В качестве движка используется **PostgreSQL** с расширением **TimescaleDB** для высокопроизводительной обработки временных рядов.

## 1. Таблицы и структура данных

### 📱 Таблица devices (Устройства)
Хранит информацию о физических контроллерах или модулях ввода-вывода (например, ADAM-6017).

*   **id (SERIAL):** Уникальный ключ.
*   **name:** Название устройства.
*   **ip_address / port:** Сетевые реквизиты для опроса по протоколу Modbus TCP (по умолчанию порт 502).
*   **is_active (BOOLEAN):** Флаг включения/выключения опроса устройства.

### ⚙️ Таблица sensor_settings (Настройки датчиков)
Связующее звено между «железом» и бизнес-логикой. Содержит параметры нормализации сигналов и метаданные.

*   **sensor_id:** Уникальный ключ.
*   **device_id:** Привязка к конкретному устройству (Связь 1:N).
*   **port_number:** Физический адрес/регистр на устройстве.
*   **slug:** Уникальный строковый идентификатор (например, `temp_main`) для быстрого обращения из кода и API.
*   **data_type:** Природа сигнала (`ANALOG`, `DIGITAL`, `VIRTUAL`).
*   **Масштабирование:** Поля `input_min/max` и `output_min/max` позволяют линейно преобразовать «сырые» данные из регистра (0-65535) в понятные физические величины (например, 0-120°C).
*   **formula:** Текстовое поле для дополнительной математической обработки (особенно актуально для `VIRTUAL` датчиков).
*   **ui_config (JSONB):** Хранение специфичных для фронтенда настроек (иконки, цвета, лимиты).

### 📈 Таблица metrics (Временные ряды)
Главная таблица системы, преобразованная в **Hypertable** (TimescaleDB). Спроектирована для хранения миллионов записей.

*   **time (TIMESTAMPTZ):** Метка времени (Partition Key).
*   **sensor_id:** Ссылка на датчик (Связь 1:N).
*   **raw_value:** «Сырое» значение, полученное с устройства до обработки.
*   **value:** Итоговое физическое значение после применения калибровки и формул.

### 🛠 Таблица system_config (Глобальные настройки)
Централизованное управление параметрами работы Collector-сервиса.

*   **raw_retention_days / agg_retention_days:** Сроки хранения детальных данных и агрегатов.
*   **polling_interval_ms:** Глобальный интервал опроса оборудования.
*   **deadband_threshold:** «Мертвая зона» — фильтр шума. Значение игнорируется, если оно изменилось менее чем на этот порог (экономия места в БД).
*   **config_reload_interval_sec:** Периодичность обновления конфигурации датчиков в памяти сервиса без перезагрузки.

## 🔗 Связи между таблицами (ER-диаграмма словами)

*   **Devices → Sensor Settings:** Один контроллер может содержать множество датчиков. Удаление устройства ограничено (`RESTRICT`), пока за ним числятся настройки.
*   **Sensor Settings → Metrics:** У одного датчика могут быть миллионы точек данных. При удалении датчика связанные метрики удаляются автоматически (`CASCADE`).
*   **System Config:** Изолированная таблица для оперативного управления поведением всей системы сбора данных.

## 🚀 Основной функционал и автоматизация

### 🔔 Real-time уведомления (Pub/Sub)
В базу встроен механизм реактивного оповещения через механизм `NOTIFY`.

*   **Как это работает:** При каждой вставке новой записи в таблицу `metrics` срабатывает триггер `trg_notify_metric`.
*   **Что происходит:** БД генерирует JSON-пакет и отправляет его в канал `metrics_realtime`.
*   **Зачем это нужно:** WebApi (или другие микросервисы) подписываются на этот канал и мгновенно транслируют данные на UI через SignalR, исключая необходимость тяжелых и частых SELECT-запросов.

### ⏳ Оптимизация хранения (TimescaleDB)
Таблица `metrics` автоматически разбивается на временные «чанки». Это обеспечивает:
1.  **Мгновенную очистку:** Удаление старых данных происходит на уровне файловой системы (drop chunk), а не строковым удалением.
2.  **Высокий Ingest Rate:** Индексы по времени всегда умещаются в RAM, что позволяет сохранять тысячи метрик в секунду.
3.  **Сжатие:** Возможность включения нативного сжатия TimescaleDB для старых данных (до 90% экономии места).

### 🔄 Масштабируемость и Гибкость
Использование типа `VIRTUAL` и поля `formula` позволяет строить «вычисляемые» системы. Вы можете создать виртуальный датчик «КПД», который будет вычисляться на лету на основе данных от пяти физических сенсоров, обеспечивая гибкую аналитику без изменения архитектуры сборщика.
