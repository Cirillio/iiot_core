**Статус:** Draft
**Сложность:** Middle+
**Стек:** .NET 10, PostgreSQL (TimescaleDB), SignalR, Dapper.

## Введение
В этой лабораторной работе вы реализуете "сердце" системы мониторинга — шлюз, который связывает промышленное оборудование, базу данных и пользовательский интерфейс. Ваша задача — не просто написать код, а построить отказоустойчивую архитектуру потоков данных.

## 📚 Необходимая теория и Материалы
Перед началом работы ознакомьтесь со следующими концепциями. Они критически важны для выполнения заданий.

1.  **PostgreSQL LISTEN/NOTIFY**: Механизм асинхронных уведомлений в БД.
    *   *Что гуглить:* `PostgreSQL LISTEN NOTIFY manual`, `sql trigger after insert`.
2.  **ASP.NET Core BackgroundService**: Как запускать долгие фоновые задачи.
    *   *Что гуглить:* `MS Docs BackgroundService`, `IHostedService lifecycle`.
3.  **Npgsql Event Handling**: Как драйвер C# работает с событиями Postgres.
    *   *Что гуглить:* `Npgsql Waiting for notifications`, `NpgsqlConnection.WaitAsync`.
4.  **SignalR Hubs**: Принципы работы веб-сокетов в .NET.
    *   *Что гуглить:* `SignalR Hub generic interface`, `IHubContext injection`.
5.  **Dapper & JSONB**: Как мапить JSON-столбцы Postgres в объекты C#.
    *   *Что гуглить:* `Dapper TypeHandler`, `Npgsql map jsonb to POCO`.

## Задача №1: Реактивность на уровне БД

**Цель:** Заставить базу данных самостоятельно сообщать внешнему миру о том, что в таблицу `metrics` поступили новые данные. Это избавит нас от бесконечного опроса (polling) базы.

**Техническое задание:**
1.  Откройте файл `iiot_init.sql` (или подключитесь к БД через IDE).
2.  Напишите SQL-функцию (Stored Procedure), которая будет вызываться триггером.
    *   Функция должна формировать JSON-объект из новых данных (`NEW.sensor_id`, `NEW.value`, `NEW.time`). *Подсказка: используйте функцию `json_build_object`.*
    *   Функция должна отправлять этот JSON в канал с именем `metrics_realtime` используя команду `pg_notify`.
3.  Напишите SQL-триггер, который срабатывает `AFTER INSERT` на таблице `metrics` и вызывает вашу функцию.

**Критерий приемки:**
Выполните `INSERT INTO metrics ...` в консоли SQL. В логе событий БД (или во вкладке "Notifications" вашей IDE) должно появиться сообщение с JSON-payload.

## Задача №2: Фоновый слушатель (The Listener)

**Цель:** Реализовать сервис внутри ASP.NET Core, который держит постоянное соединение с БД и "слушает" канал `metrics_realtime`.

**Архитектурная справка:**
В .NET для долгоживущих процессов используется `BackgroundService`. Он запускается один раз при старте приложения и работает до его остановки.

**Шаги реализации:**
1.  Создайте класс `PgNotificationWorker`, наследуемый от `BackgroundService`.
2.  **Подключение:** В методе `ExecuteAsync` создайте подключение `NpgsqlConnection`. Обратите внимание: это подключение будет занято прослушиванием, его нельзя использовать для обычных запросов.
3.  **Подписка:** Подпишитесь на событие `.Notification` объекта подключения. В обработчике события вы пока можете просто логировать полученный payload (`Console.WriteLine`).
4.  **Команда LISTEN:** Чтобы события начали приходить, нужно выполнить SQL-команду `LISTEN metrics_realtime` через `NpgsqlCommand`.
5.  **Цикл ожидания:** Реализуйте бесконечный цикл `while`, который держит соединение открытым.
    *   *Важно:* Не используйте `Thread.Sleep()`. Используйте асинхронное ожидание события `conn.WaitAsync(token)`, которое предоставляет драйвер Npgsql. Это эффективно освобождает поток, пока нет сообщений.
6.  **Resilience (Устойчивость):** Оберните логику подключения в блок `try-catch`. Если соединение разорвалось (БД перезагрузилась), сервис должен подождать 5 секунд и попытаться подключиться снова.

**Критерий приемки:**
При запуске приложения в логах видно "Connected". При ручном INSERT в БД, в логах приложения появляется JSON строки.

## Задача №3: Трансляция в Web (SignalR)

**Цель:** Переслать полученный JSON из `PgNotificationWorker` всем подключенным веб-клиентам.

**Шаги реализации:**
1.  **Создание Хаба:** Создайте папку `Hubs` и класс `MonitoringHub`.
    *   Определите интерфейс `IMonitoringClient`, содержащий метод `Task ReceiveMetrics(string json)`.
    *   Отнаследуйте хаб от `Hub<IMonitoringClient>`. Это даст строгую типизацию.
2.  **Внедрение зависимостей:** Вернитесь в `PgNotificationWorker`.
    *   Заинжектите в конструктор `IHubContext<MonitoringHub, IMonitoringClient>`.
    *   *Внимание:* Вы не можете инжектить сам `MonitoringHub` в синглтон-сервис, только `IHubContext`.
3.  **Broadcasting:** В обработчике события (где вы делали `Console.WriteLine`) вызовите метод хаба: `_hub.Clients.All.ReceiveMetrics(...)`.

**Критерий приемки:**
Код компилируется. Архитектурная цепочка "БД -> Воркер -> Хаб" замкнута.

## Задача №4: Управление конфигурацией (JSONB & Dapper)

**Цель:** Научиться работать со сложными структурами данных. Настройки UI хранятся в БД как JSON, но в коде C# нам нужны объекты.

**Техническое задание:**
1.  **DTO:** Создайте классы моделей, соответствующие таблице `sensor_settings`. Поле `ui_config` должно быть представлено отдельным классом (например, `SensorUiConfig`).
2.  **Type Handler:** Напишите `SqlMapper.TypeHandler<T>` для Dapper, который умеет конвертировать строку JSON из БД в объект C# и обратно (используя `System.Text.Json` или `Newtonsoft`).
3.  **Repository:** Реализуйте метод получения дерева устройств (`GetDevicesWithSensors`).
    *   Используйте SQL `JOIN` между `devices` и `sensor_settings`.
    *   Используйте Dapper Multi-Mapping (`QueryAsync<Device, Sensor, Device>`), чтобы собрать плоскую таблицу в иерархию объектов.
4.  **API Endpoint:** Реализуйте `PUT` метод для обновления настроек датчика.
    *   Добавьте валидацию: `Min < Max`.
    *   После обновления в БД, отправьте уведомление через SignalR (`ConfigUpdated`), чтобы клиенты перечитали настройки.

**Критерий приемки:**
GET-запрос возвращает корректный JSON, где поле `uiConfig` — это объект, а не строка.

## Задача №5: Оптимизация аналитики

**Цель:** Реализовать API для графиков, который автоматически выбирает источник данных (сырые данные или агрегаты) в зависимости от запрошенного периода.

**Шаги реализации:**
1.  Изучите структуру таблицы `metrics` и материализованного представления `metrics_hourly` в файле `iiot_init.sql`.
2.  Реализуйте метод API, принимающий `sensorId`, `from`, `to`.
3.  **Логика выбора:**
    *   Если интервал (`to - from`) больше 48 часов — запрос должен идти к `metrics_hourly`.
    *   Иначе — к таблице `metrics`.
4.  **Формат данных:** Графики (ECharts) любят массивы массивов: `[[time, value], [time, value]]`. Постарайтесь сформировать такой ответ сразу на уровне Dapper (через `Select(x => new object[] { ... })`), чтобы не гонять лишние имена полей в JSON.

**Критерий приемки:**
Запрос за месяц выполняется быстро (использует агрегаты), запрос за час возвращает детальные данные.
